### Ordering / sequencing

**Array order only.** There are no `next`/`prev` pointers anywhere in the file,
and no graph edges.

- `stage.order` is a real integer (1–4) and is the only populated order field.
- `module.order` is `null` for every module.
- `concept.order` is `null` for **all 156** concepts.

The generator sorts concepts by `(order, sourceFile)` at build time and then
freezes that into array position — since `order` is universally null, the
effective sort key is `sourceFile.localeCompare()`, i.e. **alphabetical by
source path**. Consumers must preserve array order; sorting by `order` would
collapse the sequence.

> Consequence for sequencing work: inserting an assessment node "after lesson X"
> means splicing at an array index. There is no ordinal to write to, and adding
> one would be ignored by the existing UI unless the renderer is also changed.

### Identity: `id` is NOT unique — `sourceFile` is

This is the single most important schema fact for linking assessments.

`concept.id` is `slugify(basename)`, so it collides both globally **and within a
single module**:

| Duplicate `id` | Occurrences (global) |
|---|---:|
| `introduction` | 23 |
| `exam` | 12 |
| `qiskit-implementation` | 3 |
| `quantum-teleportation` | 2 |
| `classical-information` | 2 |
| `quantum-information` | 2 |
| `vqe` | 2 |

Collisions **inside one module**, e.g. `courses-basics-of-quantum-information`
alone holds 18 concepts but only 11 distinct ids:

```
introduction          x4   (entanglement-in-action/, multiple-systems/,
                            quantum-circuits/, single-systems/)
qiskit-implementation x3
classical-information x2
quantum-information   x2
```

`sourceFile` is unique across all 156 and is what the existing code already keys
on (`RoadmapGraph` uses `key={concept.sourceFile}`, progress and deep-links use
`#learner-module/<sourceFile>`).

**Any assessment linkage must key on `sourceFile`, or on
`(stageId, moduleId, conceptId)` as a composite. A bare `conceptId` is ambiguous
and will mis-attach — `introduction` alone would match 23 different lessons.**
This is already documented at the top of `src/pages/learning-center/types.ts`.

## 3. ⚠️ `exam` ALREADY EXISTS as a distinct node type

**Confirmed: it is a first-class `type` value, not a plain lesson.**

`concept.type` has exactly two values across all 156 concepts:

| `type` | Count |
|---|---:|
| `concept` | 144 |
| **`exam`** | **12** |

The 12 exam nodes, all sourced from a course-level `exam.mdx`:

| `id` | `title` | Module |
|---|---|---|
| `exam` | `Exam \| Basics of quantum information` | basics-of-quantum-information |
| `exam` | `Exam \| Use a quantum computer today` | use-a-qc-today |
| `exam` | `Exam for Fundamentals of quantum algorithms` | fundamentals-of-quantum-algorithms |
| `exam` | `Exam \| Quantum diagonalization algorithms` | quantum-diagonalization-algorithms |
| `exam` | `Exam \| Variational algorithm design` | variational-algorithm-design |
| `exam` | `Exam \| Foundations of quantum error correction` | foundations-of-quantum-error-correction |
| `exam` | `Exam  \| General formulation of quantum information` | general-formulation-of-quantum-information |
| `exam` | `Exam \| Integrating quantum and high-performance computing` | integrating-quantum-and-hpc |
| `exam` | `Exam \| Quantum business foundations` | quantum-business-foundations |
| `exam` | `Exam \| Quantum chemistry with VQE` | quantum-chem-with-vqe |
| `exam` | `Exam \| Quantum computing in practice` | quantum-computing-in-practice |
| `exam` | `Exam \| Quantum machine learning` | quantum-machine-learning |

**Do not introduce a second type for assessments.** Points to note:

1. `type: "exam"` is set by `scripts/fetch-learning-content.js`, which assigns
   `"exam"` when the filename starts with `exam.` and `"concept"` otherwise. Any
   new type would be erased on the next `npm run fetch-content` run unless the
   generator is changed too.
2. **All 12 exam nodes share the literal id `"exam"`.** They are distinguished
   only by `sourceFile`. Adding assessments keyed by `id` would collide across
   all 12.
3. These are **course-level** exams (one per course, from `exam.mdx`), whereas
   the 56 `tests_data` assessments are **per-lesson**. Different granularity —
   they are not the same thing and one cannot replace the other.
4. The existing `exam.mdx` content is IBM's exam *landing page* (badge/enrolment
   prose), **not** question banks. The generated `assessment.md` files are the
   only actual questions present.
5. `RoadmapGraph.tsx` does not branch on `type` at all — exam nodes currently
   render identically to concepts. Nothing downstream distinguishes them yet, so
   the type is currently carried but unused.

**Recommended:** reuse `type: "exam"`, or add one new sibling value
(e.g. `"assessment"`) for the per-lesson granularity — and update the generator's
classifier in the same change so it survives a refetch.

## 4. ID / slug mismatch risk — **reconciliation is required**

Measured, not estimated. Of the 56 assessment files:

| Join attempt | Matches | Rate |
|---|---:|---:|
| directory slug == some `concept.id` | 30 | 54% |
| frontmatter `concept:` == some `concept.title` (case-insensitive) | 22 | 39% |
| **either of the above** | **32** | **57%** |
| **unmatched by both** | **24** | **43%** |

### 4a. `module:` prefix mismatch (systematic, easy)

Frontmatter uses the bare course slug; `learning-content.json` uses a prefixed id.

| assessment `module:` | learning-content `module.id` |
|---|---|
| `basics-of-quantum-information` | `courses-basics-of-quantum-information` |
| `fundamentals-of-quantum-algorithms` | `courses-fundamentals-of-quantum-algorithms` |
| `general-formulation-of-quantum-information` | `courses-general-formulation-of-quantum-information` |

Mechanical: prepend `courses-`. All 3 resolve.

### 4b. 24 assessment slugs correspond to no lesson at all

These are the blocker. They look like generation-run artifacts rather than real
Qiskit lessons:

```

  circuits-detail, final-batch-3, final-batch-4,
  info-detail, info-detail2, information-detail

Names like `final-batch-3` and `sho-detail4` have no counterpart in the Qiskit

## 6. Summary for the merge step

**Safe to rely on**

- `concept.sourceFile` — unique across all 156, already the de-facto key in the UI.
- `type: "exam"` — an existing, generator-produced value; reuse it.
- `assessment.md` internal structure — highly regular (5×`### Q<n>` with A–D +
  `**Correct:**` + `**Explanation:**`; 2×`### Challenge <n>` with a JSON
  `**Target:**` and Python starter), so parsing is mechanical.

**Must be resolved before merging**

1. Never key on `concept.id` — it collides 23× for `introduction` and 12× for
   `exam`, even within one module. Use `sourceFile`.
2. Decide the fate of the **24 unmatchable assessment slugs** (43%) — map or drop.
3. Prefix `module:` with `courses-` to join to `module.id`.
4. Handle the empty file, the misnamed `.ipynb`, and its duplicate.
5. Ignore `modules/index.md`.
6. Sequencing is **array position only** — `order` is null on all 156 concepts
   and on all 16 modules, so any inserted assessment node must be spliced at an
   index, not given an ordinal.
7. Whatever `type` is chosen, update `scripts/fetch-learning-content.js`'s
   classifier too, or the next `npm run fetch-content` will overwrite it.
